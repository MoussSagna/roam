# ROAM API — Database schema

The PostgreSQL data model of the ROAM backend (task API-03), defined in
[`apps/api/prisma/schema.prisma`](../prisma/schema.prisma) — the source of truth. It prepares the data the next
tasks need (catalog, provenance, enrichment, users, journeys, favorites, feedback) **without any business logic or
endpoint**. Domain concepts are defined in [`appdocs/domain/`](../../../appdocs/domain/DOMAIN_OVERVIEW.md); this document
explains how they are stored.

Status: both migrations are **applied to a local PostgreSQL 18.6** (database `roam`) and the model is tested on a real
database (`pnpm test:db`, database `roam_test`) — see "Local PostgreSQL" and "Tests" below.

## Overview

```text
                                ┌───────────── Provider ─────────────┐
                                │                                    │
                         ExternalSource (provenance, one per provider record)
                          │            │              │
 Category ── PlaceCategory ── Place ── ExperiencePlace ── Experience ── ExperienceCategory ── Category
                              │   │                       │   │   │
                              │   └── Event ──────────────┘   │   └── RoamEnrichment (ROAM-owned context)
                              └── RoamEnrichment              │
                                                              ├── JourneyStep ── Journey ── JourneyFeedback
                                                              └── Favorite            │           │
                                                                     │                │           │
                                              User ── UserPreference └──── User ──────┴───────────┘
```

18 tables, 14 enums, 25 foreign keys, 3 CHECK constraints. Conventions: UUID v7 ids (time-ordered, generated by Prisma), `createdAt`/`updatedAt` in
`timestamptz(3)` on mutable rows, tables in `snake_case` (`@@map`), columns in `camelCase`, enum values in
`UPPER_SNAKE_CASE` (mapping to the apps' lowercase values belongs to the API DTOs).

## Experience / Place / Event

- **Experience** is what ROAM recommends: a composed outing. It carries its identity, a location **anchor** (address,
  city, latitude/longitude — optional), media, schedule, pricing and quality. It is made of ordered places
  (`ExperiencePlace`) and may be tied to events.
- **Place** is a physical place, from a provider (identity, address, coordinates, photos, hours, price level, rating,
  attributes). A place can be part of several experiences and host several events.
- **Event** is time-bound (`startDate` required, `endDate`/`timezone` only when the source gives them). Its venue is a
  `Place` when known (`placeId`), and it can belong to an experience (`experienceId`, EVENT.md). One category.
- Pricing is never invented: `priceLevel` defaults to `UNKNOWN`; `priceMin`/`priceMax`/`currency` stay null without a
  source value (DATA_RULES.md).
- `isActive` on the three: a record a sync no longer finds is deactivated, not deleted, so journeys, favorites and
  history keep pointing at it.

## Provider data vs. ROAM enrichment

- **Provider facts** live on `Place` / `Event` / `Experience` columns, already **normalized** by the adapters (no raw
  provider payload is stored: provider JSON never leaves its adapter — DATA_RULES.md, PROVIDER_ARCHITECTURE.md —, and
  provider terms restrict caching).
- **Provenance** is `ExternalSource`: provider, `entityType`, `externalId`, URL, the provider's classification as
  received, confidence, `fetchedAt`, `providerUpdatedAt`. One row per provider record, so a place merged from two
  providers keeps both. Deduplication key: `(providerId, entityType, externalId)` — provider ids first (EXPERIENCE.md).
- **Providers are rows**, not an enum: a provider is added without a schema change; its adapter uses a stable `key`
  (`google_places`, `ticketmaster`, `data_gouv`…).
- **ROAM enrichment** is `RoamEnrichment`, separate from the facts so derived values stay identifiable (DATA_SOURCE_MATRIX
  "Primary owner"): atmosphere (open list), energy, suitable-for, best moments, tags, estimated duration (with
  `durationIsDerived`), its `source` (rules, curated, user feedback) and per-field `confidence` (JSON, as documented).

## Geography

Plain `latitude` / `longitude` (`double precision`), as in the documentation and the mobile `Coordinates` — **no
PostGIS** (not planned by any document). Composite `(latitude, longitude)` indexes on places and experiences serve
bounding-box queries ("near this point": filter a box, then compute distances in the service, as the mobile planning
already does). Moving to PostGIS later means adding a geography column and a GiST index next to these columns.

## User context

- `UserPreference` stores what the MVP scope collects at onboarding: interests, activities, usual budget
  (`BudgetRange`), maximum distance (km), usual company (`Company`) — all optional.
- The **per-outing context** (mood, time, budget, company, location — MVP_SCOPE.md §3,
  RECOMMENDATION.md "User context") is **not stored**: it is the input of a recommendation request. Together they will
  feed `User context → candidates → filtering → scoring → ranking` (not built).

## Journey and JourneyStep

- `Journey`: owner (`userId`), `status` (`ACTIVE` | `COMPLETED` — a draft is never saved), title, context (`mood`,
  `duration`, `budget` enums from JOURNEY.md), start location as a snapshot (`startKind`, label, detail, latitude,
  longitude), planned `startTime`/`endTime` ("HH:MM"), totals (duration, budget in euros, distance in meters),
  `currentStep`, `startedAt`, `completedAt`.
- `JourneyStep`: experience, `order` (0-based), `estimatedArrival` ("HH:MM"), durations, travel distance and mode
  (`WALK` | `METRO`). Steps are deleted with their journey.
- The planning values are computed by the service (as the mobile `lib/plan.ts` does), never by the database.

## Favorites and feedback

- `Favorite`: a user saves an experience; unique `(userId, experienceId)`.
- `JourneyFeedback`: one per journey (`journeyId` unique), 1–5 stars (`smallint`), optional comment
  (`varchar(300)`), author.

## Constraints

Declared in the schema (and the migration):

| Constraint                                                                        | Why                                                                                                                                                                                                                                    |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `users.email` unique                                                              | one account per email                                                                                                                                                                                                                  |
| `providers.key` unique                                                            | adapters find their provider by key                                                                                                                                                                                                    |
| `external_sources (providerId, entityType, externalId)` unique                    | deduplication / idempotent sync upserts                                                                                                                                                                                                |
| `experience_places (experienceId, position)` unique, PK `(experienceId, placeId)` | an ordered list of distinct places                                                                                                                                                                                                     |
| `journey_steps (journeyId, order)` unique                                         | one step per position                                                                                                                                                                                                                  |
| `journey_steps (journeyId, experienceId)` unique                                  | each experience at most once in a journey (JOURNEY.md)                                                                                                                                                                                 |
| `favorites (userId, experienceId)` unique                                         | a favorite is a set membership                                                                                                                                                                                                         |
| `journey_feedbacks.journeyId` unique                                              | one feedback per journey                                                                                                                                                                                                               |
| `journeys_one_active_per_user`: unique `userId` **where `status = 'ACTIVE'`**     | at most one active journey per user (JOURNEY.md); completed journeys are unlimited                                                                                                                                                     |
| `roam_enrichments.placeId` / `.experienceId` unique                               | one enrichment per record                                                                                                                                                                                                              |
| Foreign keys                                                                      | cascade for owned rows (steps, favorites, feedback, preferences, sources, enrichment); `RESTRICT` for experiences referenced by journeys and places used by experiences (deactivate instead); `SET NULL` for an event's optional links |

CHECK constraints (hand-written migration `20260926002147_check_constraints` — Prisma cannot declare them, and leaves
them alone when it compares the database with the schema):

| Constraint                             | Rule                                                                              |
| -------------------------------------- | --------------------------------------------------------------------------------- |
| `journey_feedbacks_rating_check`       | `rating` between 1 and 5                                                          |
| `external_sources_single_target_check` | exactly one of `placeId` / `eventId` / `experienceId`, the one `entityType` names |
| `roam_enrichments_single_target_check` | exactly one of `placeId` / `experienceId`                                         |

Two layers on purpose: the **services check first** (clear, domain-specific errors; helpers in
`src/database/domain-constraints.ts`), the **database guarantees** (every writer, concurrency). Rules that need the
domain stay in the services only:

| Rule                                                                                                      | Where                                                                                                                             |
| --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| At most one `ACTIVE` journey per user                                                                     | journey service (refuses, as the mobile `ActiveJourneyExistsError` does); the partial unique index makes a concurrent create fail |
| Journey transitions: created `ACTIVE` (a draft is never saved), then `COMPLETED` once                     | journey service (sets `startedAt`, `completedAt`)                                                                                 |
| `currentStep` within the steps; editing steps keeps status and current experience                         | journey service (JOURNEY.md "Rules")                                                                                              |
| Feedback only for a `COMPLETED` journey of the same user                                                  | feedback service                                                                                                                  |
| Feedback comment ≤ 300 characters                                                                         | DTO validation (+ `varchar(300)`)                                                                                                 |
| "HH:MM" times (`isHourMinute`)                                                                            | journey service                                                                                                                   |
| Rating 1–5, single targets (`isValidJourneyRating`, `hasSingleSourceTarget`, `hasSingleEnrichmentTarget`) | services first, CHECK constraints as the guarantee                                                                                |

**Looking up the active journey:** the partial unique index makes Prisma accept `userId` in `JourneyWhereUniqueInput`.
Always query it **with its status** — `journey.findUnique({ where: { userId, status: 'ACTIVE' } })` — never
`findUnique({ where: { userId } })`, which would match any journey of the user.

## Indexes

Beyond primary keys and the unique constraints above, only indexes tied to a documented query or a foreign key:
`places.city`, `experiences.city` (city pages), `(latitude, longitude)` on places and experiences (nearby),
`experiences.isActive` (candidate selection), `events.startDate` (what's on), `journeys (userId, status)` (current
journey, history) and the partial unique `journeys_one_active_per_user`, `external_sources (providerId, fetchedAt)` (refresh the oldest first — SYNC_CACHE_AND_COST_CONTROL),
and the foreign-key columns that are not the leading column of an existing index (PostgreSQL does not index them by
itself).

## Migrations

| Migration                          | Content                                                                          | Written by                         |
| ---------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------- |
| `20260926000000_init`              | tables, enums, keys, indexes, the partial unique index                           | Prisma, from the schema            |
| `20260926002147_check_constraints` | the three CHECK constraints                                                      | hand (`migrate dev --create-only`) |
| `20260926011137_authentication`    | `users.passwordHash`, `auth_sessions`, `password_reset_codes` (API-05, additive) | Prisma (`migrate dev`)             |

- The schema is the source of truth. `init` was exactly `prisma migrate diff --from-empty --to-schema` when committed;
  a unit test checks that every table of the schema is created by a committed migration, and on a real database `prisma migrate diff --from-config-datasource
--to-schema --exit-code` reports **no difference** (integration test) — so the next `migrate dev` will neither drop
  the CHECK constraints nor the partial index.
- The partial unique index is declared in the schema (`@@unique(..., where: { status: "ACTIVE" })`) with the
  **`partialIndexes` preview feature** of Prisma 7.10. Written by hand instead, Prisma would see an unknown index and
  generate a `DROP INDEX` in the next migration. When the feature leaves preview, only the generator line changes.
- Workflow: change `schema.prisma` → `pnpm --filter @roam/api prisma:migrate:dev --name <change>` (creates and applies
  the migration on `roam`) → commit it. Hand-written SQL: `prisma migrate dev --create-only`, edit, then `migrate dev`.
  Deployed environments: `prisma:migrate:deploy` (applies pending migrations, never resets). Status:
  `prisma:migrate:status`.
- Never `prisma migrate reset`, `db push --force-reset`, `DROP DATABASE` or `DROP SCHEMA` on a database holding data.

## Local PostgreSQL

The official development database for now: a **local PostgreSQL 18.6** (EDB installer, `/Library/PostgreSQL/18`,
port 5432) — **no Docker**.

| Database    | Used by                                                       | Content                                   |
| ----------- | ------------------------------------------------------------- | ----------------------------------------- |
| `roam`      | the API in development (`DATABASE_URL`), `prisma migrate dev` | development data — never emptied by tests |
| `roam_test` | `pnpm test:db` only (`DATABASE_TEST_URL`)                     | emptied before each integration test      |

Setup: create both databases once (`createdb roam`, `createdb roam_test`, or `CREATE DATABASE` in `psql`), copy
`.env.example` to `apps/api/.env` and fill both URLs (password URL-encoded), then `pnpm --filter @roam/api
prisma:migrate:dev`. `.env` is ignored by Git; `.env.example` holds placeholders only. `prisma migrate dev` needs the
right to create a database (it uses a temporary shadow database).

## Consistency audit (documentation ↔ schema)

Divergences found and how the schema handles them — none silently resolved; the product decisions stay open:

1. **Itinerary vs. Journey** — product docs and data domains say _itinerary_, the product built _journey_: the schema
   uses `Journey` (the specified, implemented concept). To confirm.
2. **Two feedback models** — only `JourneyFeedback` (built and specified) is modeled.
3. **`Favorite` target** — the mobile type allows place / experience / itinerary; the built feature is experience only:
   modeled on experiences.
4. **User preferences** — MVP scope (`UserPreference`) vs. built onboarding vs. "Mes préférences": the MVP scope version
   is modeled (the only one the documentation defines as stored data).
5. **Canonical Experience `Location.providerPlaceId` and `Source`** — represented relationally (`ExperiencePlace`,
   `ExternalSource`) instead of columns, so an experience can have several places and sources.
6. **Place `source` / `externalUrl`** — kept per provider record in `ExternalSource`, not duplicated on `Place`.
7. **Atmosphere** — documented as examples, stored as an open list (`String[]`); energy, audience, moments and price
   level are closed enums as documented.
8. **Journey ownership** — the mobile `Journey` has no user (single-device store); the backend needs `userId`
   (JourneyFeedback already carries one).
9. **Mobile `Experience` shape** (moods, labels, reviews, history fields) differs from the canonical model: the schema
   follows the canonical model; mapping the mock data is DATA-1.
10. **Energy / audience `UNKNOWN`** — EXPERIENCE.md lists `UNKNOWN` in both enums, NORMALIZATION_AND_ENRICHMENT.md
    does not: the schema keeps `UNKNOWN` (the superset, and DATA_RULES.md "use `UNKNOWN`/null rather than fabricated
    precision").
11. **No `DRAFT` journey status** — a draft journey is never saved (JOURNEY.md "States"): the stored statuses are
    `ACTIVE` and `COMPLETED`; the draft lives in the creation request.

## Tests

**Without a database** (`pnpm --filter @roam/api test`, also in `pnpm test`): `src/database/schema.spec.ts` — the
generated models (exactly the documented ones, none of the deferred ones), every enum against its documented vocabulary,
the unique constraints through the client types (checked by `tsc`), the committed migrations and no drift between
schema and `init`, a single `PrismaService`; `src/database/domain-constraints.spec.ts` — the service-level helpers.

**On PostgreSQL** (`pnpm --filter @roam/api test:db`, `vitest.db.config.ts`, `test/database/`): runs on
`DATABASE_TEST_URL` only — the run stops unless the database name ends with `_test` and differs from `DATABASE_URL`;
`prisma migrate deploy` is applied first; every test starts from emptied tables (`TRUNCATE`, refused outside a `_test`
database); files run one after the other.

- `migrations.db-spec.ts`: migrations applied, no difference between database and schema, tables, enums, CHECK
  constraints, partial index, delete rules.
- `domain-schema.db-spec.ts`: create/read through relations, UUID v7, defaults (`UNKNOWN`, nulls), timestamps, decimals,
  enums, every unique constraint (P2002), the three CHECK constraints, the active-journey index and its lookup, delete
  rules (cascade of what a user owns, `RESTRICT` on places/experiences/providers in use, `SET NULL` on an event's venue).
- `health.db-spec.ts`: the real application on the test database (startup connection, `/health` and
  `/health/database` → 200) and with an unreachable database (`/health/database` → 503, no password or host in the logs).

Repositories are tested on PostgreSQL too (`repositories.db-spec.ts`, API-04 —
[`REPOSITORY_ARCHITECTURE.md`](REPOSITORY_ARCHITECTURE.md)). Not covered yet: the service-level rules (no service yet).
